    1. O que é Git e o que é GitHub

    Antes de escrever a primeira linha de HTML, você vai aprender a guardar o seu trabalho do jeito que profissionais guardam: com Git.

    Git — o controle de versão

    Git é um programa que roda no seu computador e tira "fotografias" do seu projeto sempre que você pedir. Cada fotografia é chamada de commit. Com isso você consegue:

    • Ver exatamente o que mudou entre uma versão e outra do seu código;
    • Voltar no tempo se alguma coisa quebrar ("na terça-feira estava funcionando, o que eu mudei depois?");
    • Ter um histórico completo de tudo que você fez, com data e uma mensagem explicando cada passo;
    • Trabalhar em equipe sem que uma pessoa apague o trabalho da outra.

    GitHub — a nuvem do seu Git

    GitHub é um site (github.com) que guarda uma cópia do seu repositório Git na internet. Pense assim: o Git organiza o histórico no seu computador; o GitHub guarda uma cópia na nuvem, visível de qualquer lugar.

    Isso serve pra três coisas no seu curso:

    • Backup real — se seu computador tiver problema, seu trabalho está salvo online;
    • Portfólio — seu professor (e, no futuro, empregadores) enxergam seu código e seu progresso;
    • Entrega da atividade — como você vai ver a seguir, entregar a atividade aqui é justamente manter seu repositório atualizado.

    💡 Uma analogia simples

    Pense no Git como o botão "Salvar" de um editor de texto — só que em vez de sobrescrever o arquivo, cada "Salvar" (commit) fica guardado para sempre, com uma etiqueta escrita por você dizendo o que mudou. O GitHub é o Google Drive onde essa pasta cheia de versões salvas fica hospedada.

    Por que isso importa nas suas atividades

    As atividades desta aba são grandes e sem prazo fixo — você vai trabalhar nelas ao longo de várias aulas, não numa sentada só. Por isso, cada commit funciona como um checkpoint do seu progresso: se alguma coisa der errado numa aula, você não perde o que já tinha funcionando antes.

    2. Instalando o Git

    O Git precisa ser instalado uma vez só no seu computador. Escolha o seu sistema operacional:

    Windows

    1. Acesse git-scm.com e baixe o instalador (o site detecta que você está no Windows sozinho);
    2. Execute o instalador e vá clicando em "Next" — as opções padrão servem perfeitamente para começar;
    3. Ao terminar, abra o programa "Git Bash" que foi instalado — é o terminal que você vai usar em todas as atividades.

    macOS

    Na maioria dos Macs o Git já vem instalado. Para confirmar (ou instalar, se faltar), abra o Terminal e digite:

    git --version

    Se não estiver instalado, o próprio macOS vai oferecer para instalar as "Ferramentas de Linha de Comando" — aceite.

    Linux

    Abra o terminal e use o gerenciador de pacotes da sua distribuição:

    # Ubuntu / Debian sudo apt install git # Fedora sudo dnf install git

    Conferindo se deu certo

    Em qualquer sistema, digite no terminal:

    git --version

    Se aparecer um número de versão (algo como git version 2.43.0), está tudo certo.

    Configurando sua identidade

    Antes do primeiro commit, o Git precisa saber quem é você — essa informação fica gravada em todo commit que você fizer, pra mostrar quem fez cada mudança. Faça isso uma única vez:

    git config --global user.name "Seu Nome Completo" git config --global user.email "seuemail@exemplo.com"
    Dica: use o mesmo e-mail que você vai usar para criar sua conta no GitHub (próximo capítulo) — assim seus commits ficam corretamente ligados ao seu perfil.

    3. Criando sua conta e seu repositório no GitHub

    Criando a conta

    1. Acesse github.com;
    2. Clique em "Sign up";
    3. Informe seu e-mail (o mesmo que você configurou no capítulo anterior), crie uma senha e escolha um nome de usuário;
    4. Confirme seu e-mail quando o GitHub pedir.

    Criando um repositório novo

    Um repositório ("repo") é a pasta do seu projeto dentro do GitHub — cada atividade sua vai morar em um repositório separado.

    1. Logado no GitHub, clique no "+" no canto superior direito e depois em "New repository";
    2. Em Repository name, dê um nome sem espaço (ex: meu-site-saas);
    3. Deixe marcado como Public (assim seu professor consegue ver e avaliar);
    4. Marque a opção "Add a README file" — ela cria um arquivo de descrição inicial;
    5. Clique em "Create repository".

    Pegando o endereço do repositório

    Na página do repositório recém-criado, clique no botão verde "Code" e copie o endereço em HTTPS — algo como:

    https://github.com/seu-usuario/meu-site-saas.git

    Você vai usar esse endereço no Capítulo 5, para ligar sua pasta local ao GitHub.

    4. Iniciando um repositório no seu computador

    Criando a pasta do projeto

    Crie (ou entre) na pasta onde vai ficar a atividade, e abra o terminal (Git Bash, no Windows) dentro dela. Uma forma fácil: dentro da pasta, clique com o botão direito e procure a opção "Git Bash Here" (Windows) ou abra o Terminal e use cd para navegar até ela.

    git init

    Dentro da pasta do projeto, rode:

    git init

    Esse comando transforma uma pasta comum em um repositório Git. Ele cria uma pasta oculta chamada .git — é ali dentro que todo o histórico de commits vai ser guardado. Você nunca precisa mexer manualmente nessa pasta.

    Atenção: rode git init apenas uma vez, na pasta raiz do projeto. Se você rodar dentro de uma subpasta por engano, vai criar um repositório dentro de outro — se isso acontecer, apague a pasta .git extra que apareceu no lugar errado.

    git status — o comando que você mais vai usar

    A qualquer momento, rode:

    git status

    Ele mostra o que mudou na sua pasta desde o último commit. Acostume-se a rodar git status o tempo todo — antes e depois de quase todo comando deste guia.

    Os três estados de um arquivo

    EstadoO que significa
    Untracked (não rastreado)Arquivo novo, que o Git ainda não conhece.
    Staged (na área de preparação)Você marcou esse arquivo para entrar no próximo commit, com git add.
    Committed (commitado)Está salvo no histórico do repositório, com git commit.

    5. Seu primeiro commit

    Crie um arquivo simples para testar — pode ser o index.html que você vai usar na Atividade 1. Depois, siga os três passos abaixo.

    Passo 1 — git add

    Coloca o(s) arquivo(s) na área de staging (preparação para o commit):

    # adiciona um arquivo específico git add index.html # adiciona TODOS os arquivos novos/modificados de uma vez git add .

    O . significa "aqui" — ou seja, "adicione tudo que mudou nesta pasta". É o jeito mais comum de usar no dia a dia.

    Passo 2 — git commit

    Agora sim, salva de verdade os arquivos que estão staged, junto com uma mensagem explicando o que foi feito:

    git commit -m "cria estrutura inicial da página"

    A flag -m significa "mensagem" — tudo que vier entre aspas depois dela é a descrição do commit.

    ✍️ Como escrever uma boa mensagem de commit

    • Escreva no presente: "adiciona seção de preços", não "adicionei";
    • Seja específico: "corrige menu que não fechava no celular" é melhor que "correção";
    • Um commit, uma ideia — não junte "cria header e footer e corrige bug do JS" num commit só;
    • Evite mensagens genéricas como "mudanças" ou "update".

    Passo 3 — conferindo o histórico

    git log

    Mostra todos os commits já feitos, do mais recente para o mais antigo, com autor, data e mensagem. Para sair dessa tela, aperte a tecla q.

    6. Conectando ao GitHub e enviando pela primeira vez

    Até aqui, tudo que você fez existe só no seu computador. Agora vamos ligar essa pasta ao repositório que você criou no Capítulo 3.

    Passo 1 — git remote add

    Use o endereço HTTPS que você copiou do GitHub:

    git remote add origin https://github.com/seu-usuario/meu-site-saas.git

    Um remote é um "apelido" para um repositório que vive em outro lugar — nesse caso, no GitHub. origin é o nome padrão usado pela comunidade inteira para o remoto principal.

    Passo 2 — nomeando a branch principal

    git branch -M main

    Garante que sua branch (linha do tempo de commits) principal se chama main, o padrão atual do GitHub.

    Passo 3 — git push

    git push -u origin main

    Envia todos os seus commits para o GitHub. A flag -u ("upstream") faz o Git memorizar essa ligação entre sua branch local e a do GitHub — da próxima vez, basta digitar git push, sem precisar repetir tudo.

    Sobre login: o GitHub não aceita mais sua senha normal direto no terminal. Na primeira vez que você der git push, uma janela vai pedir para você entrar com sua conta pelo navegador (o mais comum hoje) — ou vai pedir um Personal Access Token, que se gera em GitHub → Settings → Developer settings → Personal access tokens. Siga as instruções que aparecerem na tela.

    Depois do push, atualize a página do seu repositório no GitHub — seus arquivos devem aparecer lá.

    7. O ciclo do dia a dia

    A partir de agora, toda vez que você for trabalhar na sua atividade, o fluxo é sempre o mesmo:

    🔁 O ciclo

    1. git status — o que eu mudei desde a última vez?
    2. git add . — prepara tudo que mudou;
    3. git commit -m "mensagem" — salva com uma descrição;
    4. git push — envia pro GitHub.

    git diff — vendo exatamente o que mudou

    Antes de commitar, você pode conferir linha por linha o que foi alterado:

    git diff

    Linhas em vermelho foram removidas, linhas em verde foram adicionadas. Aperte q para sair.

    Commits pequenos e frequentes

    Prefira vários commits pequenos e lógicos a um único commit gigante no final:

    ✅ bom git commit -m "cria estrutura HTML da página inicial" git commit -m "estiliza o cabeçalho e o menu" git commit -m "adiciona menu responsivo com JavaScript" ❌ ruim git commit -m "site pronto"

    Além de mais fácil de entender, se algo quebrar você consegue achar exatamente em qual commit o problema começou.

    8. O arquivo .gitignore

    Nem tudo que existe na sua pasta deveria ir para o GitHub — arquivos temporários, configurações locais do seu editor, ou pastas geradas automaticamente. O .gitignore resolve isso.

    Como criar

    Crie, na pasta raiz do seu projeto, um arquivo chamado exatamente .gitignore (com o ponto no início, sem extensão). Escreva uma regra por linha — cada linha é um arquivo, pasta ou padrão que o Git deve ignorar.

    .gitignore # pasta de dependências (se você usar alguma ferramenta com Node.js) node_modules/ # arquivos do sistema operacional .DS_Store Thumbs.db # arquivos de configuração do seu editor .vscode/
    Depois de criar o .gitignore, lembre de commitá-lo também: git add .gitignore e git commit -m "adiciona gitignore".

    9. Salvando suas atividades (a parte mais importante)

    As atividades desta aba não têm prazo de entrega fixo — elas são propositalmente grandes, para você desenvolver ao longo de várias aulas, no seu ritmo. Isso muda a forma como você deve pensar sobre commits.

    📌 A regra de ouro

    Cada commit é um checkpoint salvo do seu progresso. Como não existe uma data única de entrega, o commit substitui o "entreguei a atividade" — é o seu histórico de commits que mostra que você trabalhou nela ao longo do tempo.

    Rotina sugerida

    • Terminou uma parte da atividade (uma seção da página, um efeito novo, uma correção)? Faça um commit;
    • No fim de cada aula ou sessão de trabalho, sempre rode git push — garante que está salvo na nuvem, não só no seu computador;
    • Se for testar algo arriscado (mudar bastante código de uma vez), commite antes de mexer — assim, se der errado, você sempre tem para onde voltar.

    O que o seu instrutor vai olhar

    Seu instrutor vai acompanhar o histórico de commits no GitHub, não só o resultado final. Vários commits pequenos e bem descritos ao longo do tempo mostram seu processo de trabalho — é isso que comprova que a atividade foi feita por você, aos poucos, e não copiada de uma vez no último minuto.

    Resumindo: não existe "prazo" — existe seu repositório sempre atualizado. Trabalhou um pouco? Commitou e deu push. Essa é a entrega.

    10. Erros comuns e como resolver

    "fatal: not a git repository"

    Você tentou rodar um comando do Git numa pasta que não é (ou ainda não é) um repositório.

    # confira em qual pasta você está pwd # se for a pasta certa e ainda faltar iniciar: git init

    "Please tell me who you are"

    Você esqueceu de configurar seu nome e e-mail (Capítulo 2). Rode:

    git config --global user.name "Seu Nome" git config --global user.email "seuemail@exemplo.com"

    "failed to push some refs"

    O GitHub tem commits que você ainda não tem na sua cópia local (por exemplo, se você editou algo direto pelo site, ou trabalhou em outro computador). Antes de enviar de novo, traga essas mudanças:

    git pull origin main

    Depois, tente o git push de novo.

    Commitei um arquivo por engano, antes do push

    Se ainda não deu push, dá para desfazer o último commit mantendo as alterações nos arquivos (elas voltam para staging):

    git reset --soft HEAD~1

    Esqueci de dar um commit e a mensagem ficou errada

    Se for o commit mais recente e você ainda não fez push, dá para corrigir a mensagem:

    git commit --amend -m "mensagem correta"
